Wivo v1.7 — Multi-Role Dental Clinic Management System
Context
Wivo is currently a single-user Electron desktop app for tracking dental lab jobs. The owner wants to transform it into a full clinic management platform with 3 account types (dentist/owner, worker/technician, patient), role-based permissions, invoicing, payment tracking, worker income, and a patient portal. This is the biggest change since the app was created.

Current state: No authentication. Supabase uses anon key with wide-open RLS. User identity is a localStorage string. All 4 tables (jobs, patients, patient_teeth, visits) have no user_id or clinic_id. Payments are a boolean per job. .env is already gitignored.

Phased Plan
Phase 1: Auth + Login (foundation, do first)
Goal: App requires email/password login. Every query runs as authenticated user.

Database:

sql/012_profiles.sql — create profiles table (id → auth.users, full_name, role, clinic_id)
sql/013_auth_rls.sql — replace all "Allow all for anon" policies with auth.uid() IS NOT NULL
Code:

src/renderer/src/lib/supabase.ts — add auth helpers (signIn, signUp, signOut, onAuthStateChange)
New src/renderer/src/context/AuthContext.tsx — provides user/profile/signOut to app
New src/renderer/src/components/Auth/LoginPage.tsx — email+password form
New src/renderer/src/components/Auth/AuthGuard.tsx — wraps AppContent, shows login if no session
src/renderer/src/App.tsx — wrap in AuthGuard
src/renderer/src/stores/useSettings.ts — kasutajaNimi reads from profile instead of localStorage
All note authors (JobNotesPanel.tsx, NotesPanel.tsx) use AuthContext instead of settings
Result: App works exactly as before but requires login. First user becomes owner.

Phase 2: Clinic Entity + Data Isolation (after Phase 1)
Goal: All data belongs to a clinic. Multi-clinic safe via RLS.

Database:

sql/014_clinics.sql — create clinics table (name, address, phone, email, reg_code, logo_url)
sql/015_add_clinic_id.sql — add clinic_id column to jobs, patients, visits, profiles
sql/016_clinic_rls.sql — RLS policies filter by clinic_id matching user's profile
Code:

First-run wizard: create clinic, backfill all existing rows with new clinic_id
useCreateJob, useCreatePatient, useCreateVisit — add clinic_id from AuthContext
RLS handles read filtering automatically — hooks stay mostly unchanged
Result: Data isolated per clinic. No cross-clinic leaks.

Phase 3: Role-Based Permissions (after Phase 2)
Goal: Owner configures what each worker can see/do. 3 roles enforced.

Database:

sql/017_permissions.sql — create worker_permissions table (profile_id, permission key, granted boolean)
Permission matrix:

Capability	Owner	Worker	Patient
All jobs	✅	Configurable	❌
Create/edit jobs	✅	✅	❌
All patients	✅	Configurable	Own only
Patient health data	✅	Configurable	❌
Book visits	✅	✅	Own only
Dashboard/stats	✅	Configurable	❌
Payments/invoices	✅	Configurable	Own only
Manage workers	✅	❌	❌
Clinic settings	✅	❌	❌
Code:

New usePermissions() hook
Sidebar.tsx — hide items based on permissions
New WorkersPage.tsx — invite workers, toggle permissions (owner only)
App.tsx — role-based view routing (patient role → patient portal in Phase 5)
Result: Owner controls access. Workers see only what's allowed.

Phase 4: Invoicing + Payments (after Phase 3, parallel with Phase 5)
Goal: Proper invoice entity, payment records, worker income tracking.

Database:

sql/018_invoices.sql — invoices (number, status, dates, totals, tax) + invoice_lines (job_id, description, qty, price) + payments (amount, method, reference, recorded_by)
sql/019_worker_income.sql — worker_earnings table + jobs.assigned_to column
Code:

New useInvoices.ts hook — CRUD + generate from jobs
New InvoiceList.tsx, InvoiceDetail.tsx, InvoicePDF.tsx (print-friendly)
Migrate jobs.makstud boolean → proper payment records (backfill migration)
Dashboard gets "Töötaja tulu" section for owners
New sidebar item "Arved" (Invoices)
Result: Real invoicing with PDF, payment tracking by method, worker income.

Phase 5: Patient Portal (after Phase 3, parallel with Phase 4)
Goal: Patients log in via web and see their own health records.

Architecture decision: Extract renderer as a standalone Vite web app (same codebase, second build config). Patients access via URL, staff use Electron.

Database:

sql/020_patient_rls.sql — patients can only read own record, own teeth, own visits
Add profiles.patient_id FK to link patient-role user to their patient record
Code:

New vite.config.web.ts — web build without Electron
New PatientPortal/PatientLayout.tsx — minimal sidebar (Minu andmed, Visiidid, Seaded)
New PatientPortal/MyRecords.tsx — read-only profile + tooth chart
New PatientPortal/MyVisits.tsx — own visits list
Patient invitation flow: owner enters patient email → Supabase invite → patient sets password
Result: Patients see their own records via web. Read-only. No job/pricing data exposed.

Phase 6: Settings Migration + Polish (after Phase 2+)
Goal: Clinic-level settings shared across all users/machines.

Database:

sql/021_clinic_settings.sql — clinic_settings table (material_prices, pipeline_stages, calendar config as JSONB)
Code:

Split useSettings.ts into useClinicSettings() (DB, shared) and useUserPrefs() (localStorage, personal like theme)
Pipeline stages move from localStorage to DB
One-time migration reads localStorage → writes to clinic_settings on first login
Realtime subscriptions add filter: clinic_id=eq.{id} for performance
Result: All staff see same prices, pipeline, calendar config. Personal prefs stay local.

Key Risks
RLS policy mistake locks everyone out → test in Supabase staging project first, keep service-role escape hatch
localStorage settings lost on migration → Phase 6 includes one-time migration
Existing data has no clinic_id → Phase 2 backfills all rows on first owner login
Patients can't install Electron → Phase 5 adds web build
Every hook does select('*') with no pagination → acceptable for solo clinic, add pagination later
Verification

Run npx tsc --noEmit — must pass
Run npx electron-vite build — must succeed
Manual test: login flow, data visibility per role, RLS enforcement
Check Supabase dashboard → Auth → Users to verify role assignments
For Phase 5: deploy web build, test patient login in browser
